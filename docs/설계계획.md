## 0. 목표와 이번 단계 범위

| 구분 | 내용 |
|---|---|
| 해결할 불편 | 공장 관리자가 로봇 도입 시 바퀴·로봇팔·검사 모듈 조합을 고르기 어렵고, 도입비 대비 회수 기간 계산이 복잡함 |
| 이번 단계(3차시) | 조건 입력 → DB의 모듈 중 최적 조합 추천 → 투자 회수 기간 계산 → 결과 저장·조회 |
| 다음 단계로 미룸 | 자연어 입력(Claude API, 4차시), ROI 그래프·안전 체크리스트 리포트(5차시) |
| 형태 | Next.js 웹앱 + Supabase DB (키가 없으면 로컬 파일 저장으로 자동 전환) |

## 1. UI 설계

디자인 원칙: 애플 스타일 미니멀 · 연회색 배경(#f5f5f7) · 테두리 없는 흰 카드 · 크고 단순한 버튼(hover 시 살짝 어두워짐)

| 영역 | 구성 요소 |
|---|---|
| 헤더 | 서비스명 "ModuLink-AI", 한 줄 설명, DB 연결 상태 배지(주황=로컬 저장 / 초록=Supabase 연결) |
| ① 작업 조건 입력 | 작업 이름, 이송 하중(kg), 1회 이동 거리(m), 외관 검사 수준(없음/기본/정밀), 로봇팔로 집는 무게(kg), 대체 인원(명), 1인당 연 인건비(만원), [최적 조합 추천받기] 버튼 |
| ② 추천 결과 | 모듈 카드 3개(주행 베이스 / 로봇팔 / 검사 센서), 핵심 지표 3개(총 도입비 / 연간 순절감액 / 투자 회수 기간), 계산 근거 설명, [저장하기] 버튼 |
| ③ 저장된 검토 기록 | 저장 시각·조건·조합·도입비·회수 기간 목록, 항목별 [삭제] 버튼 |

## 2. 로직 설계

### 2-1. 모듈 선택 규칙
1. **검사 센서**: 검사 수준(기본/정밀)에 맞는 센서 중 가장 저렴한 것. "필요 없음"이면 생략
2. **로봇팔 후보**: 가반 하중 ≥ 집는 무게 × 안전율 1.2 인 로봇팔 (집는 무게 0이면 로봇팔 없음)
3. **주행 베이스 후보**: 적재 용량 ≥ (물품 + 로봇팔 자중 + 센서 자중) × 안전율 1.2
4. **호환성 검사**: 로봇팔 장착 규격(A/B)이 베이스가 지원하는 규격에 포함될 것
5. 조건을 만족하는 모든 조합 중 **모듈 합계 가격이 가장 낮은 조합**을 추천
6. 만족하는 조합이 없으면 "조건을 낮춰 보세요" 안내

### 2-2. 비용·ROI 계산
| 항목 | 계산식 |
|---|---|
| 총 도입비(CAPEX) | 모듈 합계 × (1 + 설치·연동비 15%) |
| 연간 인건비 절감 | 대체 인원 × 1인당 연 인건비 |
| 연간 순절감액 | 인건비 절감 − 유지보수비(도입비의 8%/년) |
| 투자 회수 기간 | 도입비 ÷ (연간 순절감액 ÷ 12) → 개월 (12개월 이상은 년 단위 표시) |
| 색상 표시 | 24개월 이하 초록 / 48개월 이하 주황 / 초과·회수 불가 빨강 |

> 안전율·설치비율·유지보수율은 `recommend.ts` 의 `RULES` 상수로 분리 → 현장 기준에 맞게 쉽게 수정
> 저장 시에는 서버(Server Action)에서 입력값으로 **다시 계산**해 저장 → 화면 값을 그대로 믿지 않음

## 3. DB 설계 (Supabase · PostgreSQL)

### `modules` — 모듈 카탈로그
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint (PK) | 자동 증가 |
| category | text | base / arm / sensor |
| name | text | 모듈명 |
| payload_kg | numeric | 베이스: 적재 용량 / 로봇팔: 가반 하중 |
| self_kg | numeric | 모듈 자체 무게 |
| price | numeric | 단가(만원) |
| mount | text | 장착 규격 (예: "A,B") |
| spec | text | 사양 요약 |
| level | text | 센서 검사 수준 (basic / precise) |

### `recommendations` — 추천 검토 기록
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint (PK) | 자동 증가 |
| created_at | timestamptz | 저장 시각 |
| task_name, load_kg, distance_m, inspection, pick_kg, workers, labor_cost | text/numeric | 입력 조건 |
| combo | jsonb | 추천 조합 {base, arm, sensor} |
| capex, annual_saving, payback_months | numeric | 계산 결과 |

- 접근 권한(RLS): 시연용으로 모듈 읽기, 기록 읽기·저장·삭제 허용 → 실서비스 전환 시 로그인 사용자별로 제한
- DB 미연결 시 로컬 파일(`data/local-db.json`)로 자동 전환 → 키 설정 전에도 시연 가능
- 테이블 생성 SQL: `supabase/migrations/001_init.sql`

## 4. 확장 고려 (다음 회차 계획)

| 회차 | 추가 기능 | 준비된 구조 |
|---|---|---|
| 4차시 | 자연어 입력 → Claude API가 조건(하중·검사 등)으로 변환 → 기존 추천 로직 재사용 | 추천 로직이 입력값 객체만 받도록 분리되어 있음 |
| 4차시 | Claude API 호출은 서버(Server Action)에서만 → 키 노출 없음 | `features/` 아래에 `ai/` 기능 폴더만 추가 |
| 5차시 | 월별 누적 절감액 ROI 그래프, 안전 기준(ISO 3691-4, KCs) 체크리스트 리포트 | 결과가 DB에 구조화되어 저장됨 |
| 이후 | 실제 ModuLink 모듈 사양 등록, 서드파티 모듈 제조사 등록 창구 | 모듈은 코드가 아닌 DB에서 관리 |

## 5. 코드 구조 (기능 단위 분리 → 확장 용이)

| 계층 | 파일 | 역할 |
|---|---|---|
| UI | `src/app/page.tsx` | 서버에서 모듈·기록을 읽어 화면 구성 |
| UI | `src/components/Planner.tsx` | ① 조건 입력 ② 추천 결과 (즉시 계산) |
| UI | `src/components/HistoryList.tsx` | ③ 저장된 기록 + 삭제 |
| 로직 | `src/features/modules/recommend.ts` | 추천·ROI 계산 (순수 함수, 화면/서버 공용) |
| 서버 | `src/features/recommendations/actions.ts` | 저장·삭제 Server Action |
| 데이터 | `src/features/*/repository.ts` | DB 접근을 한 곳에 모음 (Supabase ↔ 로컬 파일 교체 가능) |
| DB | `src/lib/supabase/server.ts` | Supabase 클라이언트 (키 없으면 null) |
| DB | `supabase/migrations/001_init.sql` | 테이블·예시 데이터·권한 |

※ 모듈 사양과 가격은 시연용 예시 값입니다.
